# 播客核心思想跟踪产品调研与 PRD

调研日期：2026-04-24

## 1. 产品一句话

做一个面向知识工作者和团队的「播客情报自动化平台」：用户配置需要跟踪的播客、主题、人物、公司或关键词后，系统持续发现新单集和相关内容，自动转录、筛选、提炼核心思想，并输出可验证、可订阅、可协作的结构化简报。

核心不是“把一集播客总结一下”，而是“持续帮用户监听播客世界里和我有关的新信号”。

## 2. 背景与问题

播客的价值密度很高，但消费成本也高。一次完整收听通常需要 30-120 分钟，而且音频内容很难检索、复盘和团队共享。现有 AI 摘要产品已经能解决“给我一个链接，帮我总结”这一层问题，但对你的需求来说还不够：

- 你希望用户只配置一次主题或播客，后续有更新就自动触发。
- 你希望不仅支持“已关注播客更新”，还支持“搜索到新的相关内容”。
- 你希望结果不是泛泛摘要，而是围绕用户关心的问题抽取核心思想、证据、时间戳和行动建议。
- 你希望这是产品化能力，不是个人脚本。

## 3. Office Hours 六问压实

### 3.1 真实需求是什么

用户不是想“少听播客”，而是想降低信息遗漏和信息整理成本。核心需求是：

- 不错过关注领域里的新观点。
- 快速判断一集是否值得听。
- 把播客里的观点变成可搜索、可引用、可分享的知识资产。
- 对团队而言，把音频情报接入 Slack、飞书、Notion、知识库或 CRM。

### 3.2 用户现在怎么解决

现状通常是：

- 手动在小宇宙、Apple Podcasts、Spotify、YouTube 找节目。
- 靠标题、shownotes 或评论判断是否值得听。
- 复制链接到 BibiGPT、Podwise、NotebookLM、ChatGPT 等工具做单次摘要。
- 重要内容再手动同步到 Notion、Obsidian、飞书文档。

问题是工作流割裂，且不能持续跟踪。

### 3.3 谁最痛

优先用户不应是泛播客听众，而是“播客内容对工作产出有直接价值”的人：

- 投资研究员：跟踪 AI、消费、医疗、出海、二级市场观点。
- 产品/技术负责人：跟踪 AI agent、开发者工具、SaaS、竞品访谈。
- 内容编辑/知识博主：持续发现可写选题和观点素材。
- PR/市场/品牌团队：跟踪公司、竞品、高管、产品在播客中的出现和评价。
- 学习型个人用户：跟踪固定播客并沉淀个人知识库，但这不是首个付费主战场。

### 3.4 最窄切口

MVP 不做通用播放器，不做全平台内容库，不做社交社区。

最窄切口建议：

> 面向中文/双语 AI 与科技从业者的播客主题雷达：配置 5-20 个播客或主题，每天/每周自动生成“新观点简报”，每条观点带来源、时间戳、相关原文片段和是否值得听。

### 3.5 应该观察什么

MVP 需要尽快验证这些行为：

- 用户是否愿意花 5 分钟配置关注主题。
- 用户是否每周打开简报超过 2 次。
- 用户是否点击时间戳回听原音频。
- 用户是否把摘要导出或转发给团队。
- 用户是否修改提示词、过滤规则和关注源。
- 用户是否因为“错过重要观点”愿意付费。

### 3.6 未来形态

如果切口成立，产品可以从“播客摘要”升级为“音频情报操作系统”：

- 跨播客、视频、会议、直播的主题监听。
- 个人/团队语义知识库。
- 观点图谱：谁在什么时候对什么主题表达了什么立场。
- API/webhook：让企业把播客信号接入研究、销售、PR、投研和内容工作流。

### 4.3 竞品结论

这个市场已经不缺“播客摘要器”。如果只做“输入链接，输出摘要”，会直接撞上 Podwise、BibiGPT、Snipd、Deciphr、Podsqueeze、NotebookLM 等产品。

更好的切入点是：

- 从 episode-centric 转为 topic-centric。
- 从 user-pull 转为 system-push。
- 从 summary 转为 intelligence brief。
- 从个人效率工具转为团队可协作的情报流。
- 从“AI 说了什么”转为“AI 引用音频证据告诉你为什么可信”。

## 5. 产品定位

### 5.1 目标用户

第一阶段优先：

- AI/科技/商业领域知识工作者。
- 投研、产品、技术、内容团队。
- 关注 5-50 档播客或 5-20 个主题的人。
- 每周至少听 3 小时播客，且播客内容会影响工作判断或输出。

暂不优先：

- 只想听娱乐播客的泛用户。
- 只需要单集摘要的轻度用户。
- 播客创作者的一站式分发/剪辑/营销需求。

### 5.2 核心价值主张

> 你告诉我关注什么，我持续帮你听。每次有新内容或新观点出现，我给你带证据的核心思想简报。

### 5.3 北极星指标

每周被用户保存/转发/回听的高价值观点数。

可操作定义：

- `valuable_insights_per_active_user_per_week`
- 高价值行为包括：保存、导出、分享、点击时间戳回听、加入知识库、标记为重要。

## 6. MVP 范围

### 6.1 MVP 必须有

#### A. 关注配置

用户可以创建 Watch：

- 关注播客：输入 RSS、Apple Podcasts、Spotify、YouTube、小宇宙节目/单集链接。
- 关注主题：输入自然语言主题，例如“AI agent 商业化”“Claude Code 最佳实践”“中国消费创业”。
- 关注实体：人物、公司、产品、基金、项目、技术名词。
- 设置过滤条件：语言、来源、节目列表、排除词、最低相关性、最大处理时长。
- 设置触发频率：实时、每日、每周。

#### B. 内容发现

系统发现内容的方式：

- RSS 轮询：优先支持公开 RSS，这是最稳定和合规的基础。
- Listen Notes API：用于播客/单集搜索、元数据补全和主题发现。
- 小宇宙公开页面解析：MVP 可支持公开页面链接解析，但需要明确标注为 best-effort，并为后续合规接入或用户授权预留接口。
- 手动链接输入：支持用户粘贴单集链接立即处理。

#### C. 触发决策

不是发现任何新单集都全量转录。MVP 应有两级筛选：

- 轻筛：标题、shownotes、嘉宾、节目名、发布日期与主题规则匹配。
- 深筛：必要时转录前 5-10 分钟或抽样片段，判断是否值得全量处理。

触发类型：

- `new_episode_from_followed_podcast`
- `new_episode_matches_topic`
- `manual_url_submitted`
- `backfill_requested`
- `scheduled_weekly_digest`

#### D. 转录与分段

处理流程：

- 下载或读取音频 URL。
- 转录为带时间戳文本。
- 说话人分离，若无法可靠区分则标记为 unknown speaker。
- 按语义和时间切段，建议 3-8 分钟一段。
- 生成章节标题和段落摘要。

#### E. 核心思想抽取

每集输出：

- 一句话总结。
- 3-7 个核心观点。
- 每个观点包含论点、论据、例子、反方/限制、时间戳、置信度。
- 关键人物/公司/产品/书籍/论文/链接。
- 值不值得听：适合谁、跳听哪些片段、可以跳过的原因。
- 用户主题视角摘要：只抽取和该 Watch 相关的内容。

#### F. 简报与通知

输出形式：

- Web inbox：所有新发现和已处理内容。
- Daily digest：每日摘要。
- Weekly brief：按主题合并的周报。
- 通知渠道：邮件优先，后续 Slack/飞书/企业微信/webhook。
- 导出：Markdown、Notion、Obsidian、Readwise。

#### G. 可验证性

每条重要结论必须绑定：

- 原始单集链接。
- 时间戳。
- 转录片段摘录。
- 模型置信度。
- “听原文”入口。

MVP 不追求摘要华丽，优先追求可追溯和低幻觉。

### 6.2 MVP 不做

- 不做完整播客播放器。
- 不做社交评论社区。
- 不做播客托管或分发。
- 不做视频剪辑、shorts、audiogram。
- 不做全网版权内容抓取。
- 不做企业级品牌受众画像，除非后续切入 B2B PR。

## 7. 用户故事

### 7.1 个人研究者

作为一名 AI 产品经理，我想关注“AI agent 工作流”和 10 档海外技术播客。每当有新节目讨论 agent、MCP、Claude Code、OpenAI API，我希望每天早上收到一份中文简报，告诉我有哪些新观点、哪些值得完整听、关键时间戳在哪里。

验收标准：

- 能配置主题和节目列表。
- 每天收到不超过 10 条高相关观点。
- 每条观点有来源和时间戳。
- 能点击回听或导出 Markdown。

### 7.2 投资/行业研究团队

作为投资研究员，我想跟踪“具身智能”“AI infra”“稳定币支付”等主题，系统自动发现新播客和访谈内容，生成每周观点变化简报。

验收标准：

- 支持跨播客搜索发现。
- 同一主题下能聚合多集观点。
- 能按人物、公司、市场、技术维度分类。
- 能输出团队共享链接。

### 7.3 内容编辑

作为内容编辑，我想追踪“海外增长案例”和“创始人访谈”，系统每周帮我整理可写选题、金句和观点冲突。

验收标准：

- 能生成选题建议。
- 能提取可引用金句并带时间戳。
- 能标记“适合公众号/播客/短视频”的素材。

### 7.4 PR/品牌团队

作为品牌负责人，我想知道哪些播客提到了我们的公司、竞品或品类趋势，并在重要提及时收到提醒。

验收标准：

- 支持实体别名和排除词。
- 能返回具体提及片段。
- 能按情绪和重要性排序。
- 支持邮件或 webhook 通知。

## 8. 核心流程

### 8.1 用户配置 Watch

1. 用户输入主题、播客或实体。
2. 系统生成初始规则：关键词、同义词、相关实体、排除词。
3. 用户确认关注源和通知频率。
4. 系统开始从当前时间向后监听，可选回溯最近 30/90 天。

### 8.2 新内容发现

1. Scheduler 定时运行。
2. Source connector 拉取 RSS/API/公开页面。
3. Episode normalizer 统一元数据。
4. Deduper 按 GUID、音频 URL、标题相似度去重。
5. Relevance scorer 判断是否进入处理队列。

### 8.3 处理队列

状态机：

- `discovered`
- `queued`
- `metadata_scored`
- `audio_fetching`
- `transcribing`
- `segmenting`
- `summarizing`
- `topic_extracting`
- `quality_checking`
- `published`
- `notified`
- `failed`

失败需要可重试，且保留错误原因。

### 8.4 摘要生成

1. 先按片段提取局部观点。
2. 再按整集合并，去重和排序。
3. 最后按用户 Watch 视角重写摘要。
4. 质量检查：每条观点必须有证据片段；没有证据则降级为“可能提到”。

### 8.5 简报生成

日报：

- 今日新发现。
- 高相关观点 Top 5。
- 值得完整听的单集。
- 可以跳过但可存档的单集。

周报：

- 主题趋势变化。
- 重复出现的人物/公司/技术。
- 新出现但重要的观点。
- 多个播客之间的共识和分歧。

## 10. 非功能需求

### 10.1 准确性

- 摘要不能出现无来源的确定性断言。
- 所有关键观点必须绑定时间戳。
- 低置信度转录要提示用户。
- 支持用户反馈“错误/无关/重要”，用于优化过滤。

### 10.2 延迟

MVP 目标：

- RSS 更新发现：15-60 分钟内。
- 单集处理：60 分钟音频在 10-20 分钟内出结果，取决于模型与队列。
- 日报：用户本地时区早上固定发送。

### 10.3 成本控制

核心成本来自转录和 LLM 摘要。必须避免“发现即全量处理”。

策略：

- 先用元数据和轻量模型做相关性筛选。
- 长音频分块并缓存转录。
- 同一单集被多个 Watch 命中时共享转录和基础摘要。
- 高价值用户/团队才开启全量历史回溯。

### 10.4 合规与版权

- 优先处理公开 RSS 和用户主动提交的链接。
- 小宇宙等平台要区分公开网页解析、用户授权和官方合作三条路径。
- 不提供批量下载原音频给用户。
- 摘录只展示必要片段，不替代原内容。
- 保留原始来源链接，鼓励回到平台收听。
- 企业版需要数据删除、审计日志和权限隔离。

## 11. 质量评估

### 11.1 自动评估指标

- relevance precision：推送内容中用户认为相关的比例。
- insight groundedness：观点是否有对应证据片段。
- transcript confidence：转录平均置信度。
- duplicate rate：重复推送率。
- processing success rate：处理成功率。
- notification open rate：通知打开率。

### 11.2 人工评估样本

每周抽样 50 条 insight，人工标注：

- 观点是否准确。
- 证据是否支持观点。
- 是否有遗漏关键观点。
- 是否对 Watch 相关。
- 是否值得推送。

## 12. 商业模式

### 12.1 个人 Pro

面向知识工作者：

- 每月 N 小时转录。
- N 个 Watch。
- 日报/周报。
- Notion/Obsidian/Readwise 导出。

### 12.2 Team

面向研究、产品、内容团队：

- 团队 Watch。
- 共享 inbox。
- Slack/飞书/webhook。
- 协作评论和标签。
- 主题周报。

### 12.3 Enterprise / Intelligence

面向 PR、投研、品牌：

- 更大规模监控。
- API。
- 历史回溯。
- 实体别名管理。
- 权限、审计、数据保留策略。
- 专属转录/模型配置。

## 13. MVP 里程碑

### M0：技术验证

目标：证明一条播客链接可自动处理成可验证摘要。

范围：

- RSS/手动 URL 输入。
- 音频抓取。
- 转录。
- 分段摘要。
- 时间戳证据。
- Markdown 输出。

验收：

- 10 条不同来源播客成功处理。
- 输出中 90% 核心观点有时间戳。

### M1：Watch 与自动触发

目标：从单次处理升级为持续监听。

范围：

- Watch 配置。
- RSS 轮询。
- 新单集触发队列。
- 相关性筛选。
- 邮件日报。

验收：

- 用户配置一次后无需手动输入链接。
- 新单集可在 60 分钟内进入处理队列。

### M2：主题发现

目标：不仅监听已关注播客，也能发现新播客/新单集。

范围：

- Listen Notes API 搜索。
- 主题定时搜索。
- 去重和源质量评分。
- Topic Brief。

验收：

- 每个主题每周发现至少 5 条用户认为相关的新内容。
- 无关推送比例低于 30%。

### M3：团队工作流

目标：从个人工具变成团队情报流。

范围：

- Team workspace。
- 共享 watch。
- Slack/飞书/webhook。
- 保存、评论、标签。
- 周报导出。

验收：

- 至少 3 个团队每周使用。
- 30% 以上 insight 被保存/分享/评论。

## 14. 风险与应对

### 14.1 内容源不稳定

风险：小宇宙等平台接口和页面结构变化。

应对：

- MVP 以 RSS 和用户提交链接为主。
- 小宇宙公开页面解析作为补充。
- 设计 connector 抽象，便于替换。
- 长期寻找官方合作或用户授权。

### 14.2 AI 摘要同质化

风险：输出像普通 ChatGPT 摘要，没有产品壁垒。

应对：

- 围绕用户 Watch 生成“相关观点”，不是通用摘要。
- 强制证据、时间戳、置信度。
- 做跨单集观点聚合和趋势变化。
- 利用用户反馈训练过滤和排序。

### 14.3 成本失控

风险：全量转录所有发现内容成本过高。

应对：

- 两级筛选。
- 转录缓存。
- 多 Watch 共享处理结果。
- 按小时/credit 收费。

### 14.4 冷启动无内容

风险：用户刚配置 Watch 时看不到价值。

应对：

- 提供最近 30 天回溯。
- 内置推荐 Watch 模板。
- 预置热门科技/商业/投资播客源。

### 14.5 版权与平台关系

风险：内容处理被认为替代收听或违反平台条款。

应对：

- 不分发完整音频和完整转录。
- 摘录保持短片段且用于引用验证。
- 回链到原平台。
- 支持创作者 opt-out。
- 企业版提供合规配置。

## 15. 推荐的第一版产品决策

### 15.1 不要做“小宇宙增强版”

小宇宙已有社区、播放、评论和推荐生态，直接做增强播放器很难赢。你的产品应该站在小宇宙、Apple Podcasts、Spotify、RSS 之上，做跨源的信息层。

### 15.2 不要从 C 端泛用户开始

泛用户付费弱，需求不稳定。先服务强需求人群：投研、产品、技术、内容、PR。

### 15.3 第一版主打“主题雷达”

推荐首屏文案：

> Follow ideas, not episodes.  
> 关注一个主题，自动收到播客世界里的新观点。

### 15.4 第一版输出要像研究简报

不要只输出：

> 本期主要聊了 AI agent、创业和产品。

应该输出：

> 观点：嘉宾认为 agent 产品的分发壁垒会从模型能力转向工作流入口。  
> 证据：12:43-14:20，嘉宾用 CRM agent 的例子说明用户不会为“智能”付费，而会为“少切换系统”付费。  
> 影响：这支持“垂直工作流 agent 优先于通用助手”的产品假设。  
> 值得听：如果你正在做 B2B agent，建议听 12:43-22:10。

## 17. 下一步建议

1. 做 M0 技术验证：RSS/URL 输入到 Markdown 摘要的端到端 pipeline。
2. 访谈 10 个种子用户，优先找 AI 产品经理、工程负责人、技术内容创作者和科技投资研究者。
3. 用 20 档中英科技/AI 播客和 5 个主题跑一周离线实验，人工判断推送质量。
4. 进入工程架构设计：connector、queue、transcription、insight extraction、brief delivery、workspace data model。
5. 设计 Web App + 邮件简报的 M1 原型，验证 Watch 配置、自动发现、证据型 insight 和 30 天回溯。
